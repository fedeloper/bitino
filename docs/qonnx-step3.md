### Why one group per IR node of the deployed graph

The four transformer adapters and the detector adapter are not module-by-module mirrors of a PyTorch forward (window
partitions as row `Gather`s of constant indices, GELU replaced by a zero mask by a recipe step, BHViT's 6-D windows,
heads split by `Reshape` / `Transpose`, constant `BMatMul` operands for row sums), and their published files are the
output of passes and, for BiBERT and Bi-ViT, of a second recipe step. Writing each IR node of the **deployed** graph as
its standard-op pattern makes the canonical file the exact description of what the runtime executes, and the import a
pure pattern match with no pass afterwards; this is recorded in the file itself (`bitino.import = {"mapping":
"groups"}`), so the file alone determines its `.bitino` (the open design point of step 2: no import argument; the
only arguments are `--naming exporter --cleanup none`, which are what the importer does for such a file anyway).

The values come from the checkpoint: the exporter runs the legacy adapter on the authors' model loaded from the
checkpoint (SHA-256 checked), the converter's passes and the recipe's derive step, and **requires** that this rebuilt
graph has the published data and graph SHA-256 (the "rebuilt from checkpoint" column: true for all 39 files) before it
writes the file from it. Nothing is read from the published file except its hashes and, for the export check, the
published conversion's reference logits (the same converter, checkpoint and eval set, read only).

### The canonical patterns

Every group is the profile's pattern for its IR operator (docs/qonnx-profile.md § 4); `bitino.name` = the IR node name,
`bitino.order` = its position, `bitino.consts` = the IR name of every constant input, `bitino.ir` = the IR operator (and
input count / layout tags where the published file has them), `bitino.attrs` = JSON forms (`pad_value 0` vs `0.0`),
absent default attributes (`null`) and the float64 value of float32 attributes (LayerNorm `eps`).

| IR operator | canonical group | class |
|---|---|---|
| `BDense` | `Bin(x [− t]) → MatMul(·, W[K, O]) → [Mul(post_mul)] → [Add(post_add)]`, ±1 weights as `Cast(INT8)`, ternary (`w_zero`) as `IntQuant(Cast(INT8), 1, 0, 2, signed, narrow)` | B |
| `BMatMul` | `MatMul(Bin_a(a), [Transpose(last two)](Bin_b(b))) → [Mul(scale carrier)]`; `Bin` = `Sign` (sign_zero), `Relu(Sign)` (gt0, BiBERT's {0, 1} binarizer), `BipolarQuant` (ge), `Where(Greater)` (gt); a constant operand is `Bin(initializer)` | B |
| `BConv2D` | `Bin(x [− t]) → [Pad(v)] → Conv(·, Cast(INT8 ±1), pads 0) → [Mul] → [Add] → [Relu]` | B |
| `Gather` | `Gather(T, ids, axis 0)`; bit / ternary table with row scale: `Mul(Gather(Cast(INT8), ids), Unsqueeze(Gather(alpha, ids), −1))` | B (on `ids:<V>`, Q7) |
| `ChannelAffine`, `Add`, `AddBroadcast`, `Mul`, `Activation` (relu, sign_zero, prelu), `Reshape`, `Transpose`, `Concat`, `MaxPool2D` | themselves (`bitino.ir` names the IR operator where `Add` / `Mul` of a constant admit several) | B |
| `FakeQuant` | `Mul(Clip(Round(Add(Div(Mul(x, pre_scale), s), z)), qmin, qmax), s)` | B |
| `LayerNorm`, `Softmax` | `LayerNormalization(axis −1)`, `Softmax(axis −1)` | F |
| `Activation` gelu / tanh | `Mul(Mul(x, 0.5), Add(Erf(Div(x, √2 carrier)), 1))` (opset 17), `Tanh` | F |
| `Conv2D`, `Dense`, `MatMul`, `AvgPool2D`, `GlobalAvgPool`, `ReduceMean`, `ChannelGate` | `Conv [→ Relu]`, `Gemm` / `MatMul + Add`, `MatMul → Mul(scale)`, `AveragePool(count_include_pad)`, `GlobalAveragePool [→ Flatten]`, `ReduceMean`, `Mul(x, Cast(Sigmoid(Cast(g, DOUBLE)), FLOAT))` | F |
| `ImageGrayU8` | § 4.5: `Mul`, `Where(IsNaN)`, `Clip`, `Floor`, `Cast(INT32)`, INT32 `Mul` / `ReduceSum`, `Add(2^(s−1))`, UINT32 `BitShift` | B |
| `LocalBinaryPattern` | § 4.5: DOUBLE `Pad` / `Slice` shifted copies, `rr = Add(row index, rp_i)`, `dr = Sub(rr, Floor(rr))`, the bilinear sums in scikit-image's order, `GreaterOrEqual`, `Xor` / `LessOrEqual` / `Where` (uniform) or `Σ bit·2^i` (default), `Div` in DOUBLE, `Cast(FLOAT)`; the uniform-shift condition (Q12) checked by writer and importer | B |
| `FftLogMagnitude` | § 4.5 (Q1): DOUBLE `MatMul` DFT on float64 cos / sin tables (`Re = C X C − S X S`, `Im = −(S X C + C X S)`), `Sqrt`, fftshift as two `Gather`s, `Log(· + eps) · mul / div`, `Cast(FLOAT)`; the importer requires the tables to be `cos / sin(2π (kn mod N) / N)` in float64 bit for bit | F (float contract) |

**Layout (R3).** 4-D image tensors are NCHW in the file (the graph input, spatial operators and the per-channel /
element-wise groups between them); every other tensor keeps the IR's shape (tokens, attention maps, BHViT's 4-D
tensors that the IR reshapes from tokens, 5-D / 6-D windows). A change between the two is an explicit
`Transpose(0, 2, 3, 1)` / `Transpose(0, 3, 1, 2)` as the last node of the producer's group (of the first consumer for
the graph input); it emits no IR node. The importer derives each ONNX tensor's tag from the producing pattern, never
from metadata.

**No custom operator was needed, and no network was stopped for an inexpressible construct.** The BiBERT `{0, 1}`
binarizer is `Relu(Sign(x))`, softmax / LayerNorm / GELU are `Softmax` / `LayerNormalization` / the `Erf` form, the
image features are standard-op subgraphs. The log2 residual code (Gather on a 256-entry table or the 127-compare form)
occurs only in int8_full files (step 5); none of the 39 float files uses it.

## Verification

Per file (`tools/qonnx_step3_acceptance.py`): check-qonnx (no error, no warning); data + graph SHA-256 of the
re-imported file vs the published file (and the recipe); the C++ runtime (stages `reference` and `optimized`) on the
published and the re-imported file, every sample of the check set, bit for bit; the numpy executor (first output) on
both (the published file on the first 16 samples); the C++ reference stage of the re-imported file bit for bit
against its numpy executor; **Level 3** as in steps 1 and 2 (IR fp64 vs the QONNX graph in float64 within 1e-6, or the
deviation traced to a first binarization flip at |pre| ≤ 1e-3 × the median |pre| of that binarizer, or no flip and
max |Δ| ≤ 1e-5 × max |output|); the export check against the source framework (fp32 top-1 agreement, fp64 max |Δ|).

The float32 reference is the canonical file in one onnxruntime session with `ORT_DISABLE_ALL` (assumption A2), the
QONNX quantizers evaluated by their standard-op definitions (`BipolarQuant(x, 1) = Where(x ≥ 0, 1, −1)`, the constant
ternary `IntQuant` = identity), because qonnx `execute_onnx` (one session per node) is too slow for 39 files × 128
samples. It is cross-checked against `execute_onnx` on two samples per file (`reference_f32_vs_qonnx_execute_onnx`):
the two differ only from the first float `Conv` / `MatMul` on (see Findings).

The synthetic tests check what the full networks cannot isolate: every B-class pattern (BDense ternary with
thresholds, BMatMul gt0 and constant operands, BConv2D with threshold / explicit Pad / groups / dilation, FakeQuant,
ImageGrayU8 with NaN / ±Inf pixels, both LBP methods, the layout changes) evaluates in onnxruntime fp32 **bit for bit**
like the numpy executor, and every pattern's float64 evaluation (OnnxF64) equals the executor's to 1e-12 (1e-6 with
the gate's rounded sigmoid).

## Findings

* **Nothing needed a custom operator.** Every construct of the 29 networks is standard ONNX + the QONNX
  `BipolarQuant` / `IntQuant`; no network was stopped for an inexpressible operator. BiBERT's `{0, 1}` binarizer is
  `Relu(Sign(x))` (R1 `gt0`), the GELU zero mask of the derived variants is `Add`, `Sign`, `Mul`, `Add`, `Mul`, the
  image features are the § 4.5 subgraphs.
* **The legacy route reproduces from the checkpoints.** For every one of the 39 files the deployed graph rebuilt from
  the checkpoint in the recorded reference environment (and torch thread count) has the published data and graph
  SHA-256 (export.json → `rebuilt_vs_published`). Two reproducibility facts were needed: `tools/derive_variant.py`
  operates on the *re-read* converter file (fresh unique-name counter: the GELU-mask node names), so the exporter
  round-trips the graph through the file format before the derive step; and the FTL source tree had to be fetched
  (pinned commit, hashes = the published manifest's).
* **Byte identity holds with three representation facts**, carried by naming metadata, never by a value: IR nodes
  with trailing empty inputs (`BDense` with 5 inputs and no threshold, `BConv2D` with 5) and constant layout tags
  that differ between converters (`OI_bit` in BiBERT, empty in Bi-ViT / GSB / BHViT, `VD_bit` embedding tables):
  `bitino.ir`; absent default attributes (Bi-ViT / GSB / BHViT patch `Conv2D` without `dilations` / `groups` /
  `pad_value` / `activation`, BHViT `BConv2D` without `activation` / `output`, `Dense` without `activation`) and
  `pad_value 0` vs `0.0`: `bitino.attrs`; data sections not in first-use order (the passes' folded constants, the
  derive step's mask constants): `bitino.const_order`.
* **Semantics.** In float64 the canonical files equal the numpy executor of the published graphs to rounding
  (BiBERT 2e-15, GSB 4e-15, BHViT 6e-13, FTL 2e-8: the FTL difference is the ChannelGate's double sigmoid rounded to
  float32 in the file, as the kernel does, while the executor's float64 mode keeps it in double). In float32, every
  B-class pattern is bit-identical in onnxruntime and in the numpy executor (synthetic tests). On the full networks
  the float32 outputs of onnxruntime and of the executor differ by the expected float32 chaos of binary networks
  (binarization flips after F-class layers), which is what Level 3 traces.
* **The source models' own float32 noise** is visible in the export check and matches the legacy conversion
  reports: Bi-ViT's fp32 forward is degenerate (its fp32-vs-fp64 top-1 agreement is 0.117 in the legacy report too),
  BHViT's fp32 and fp64 forwards agree on 0.81 of the check set; where the source's fp64 forward and the binarizer
  conventions agree with the file, the fp64 export check is at rounding level.
* **A2 is not exact for float `Conv` in qonnx `execute_onnx`.** Its one-node sessions run with onnxruntime's
  default optimization level, which still picks an optimized kernel for a single `Conv` (NCHWc), so its float32
  result differs from an `ORT_DISABLE_ALL` session by rounding (Bi-ViT tiny: first difference at the patch-embedding
  `Conv`, 2.6e-4; logits up to 5.5 after Bi-ViT's chaotic binarizations). Recorded in the profile (§ 2 A2); B-class
  patterns are unaffected.
* **Memory.** qonnx `execute_onnx` keeps every activation of the graph; at 224 × 224 (BHViT, the detectors) it does
  not fit the run's budget, so its cross-check runs only on the graphs whose activations take ≤ 1 GB per sample.
  The numpy executor got a `keep=` option (frees intermediates after their last use) for the verification.

## Design decisions

1. **Import mode in the file (`bitino.import`).** Step 3 records how a file is imported in the file itself
   (`{"mapping": "groups"}`), following the open design point: the only import arguments are `--naming exporter
   --cleanup none`, which the group mapping implies. Confirm, and whether steps 1 / 2 should move their import
   arguments (`--affine keep`, `--constant-order first-use`, `--bit-outputs none`, `--flatten-dense permute`) into
   the same key (e.g. `{"mapping": "walk", "affine": "keep", ...}`), so that every canonical file determines its
   `.bitino` alone.
2. **`bitino.ir` (IR operator, input count, layout tags).** A new node key, used only where the ONNX pattern admits
   several IR operators with the same values (`Add` of a constant: `Add` / `AddBroadcast` / `ChannelAffine`), where the
   published IR node has trailing empty inputs, or where a constant's layout tag (`OI_bit`, `VD_bit`, ...) is not the
   importer's default. It never changes a value (the reader checks the pattern of the named operator). Confirm it as
   part of § 7, or prefer the importer to pick one operator per pattern and the legacy converters' files to be
   regenerated (which would change the published hashes, against the bar).
3. **The deployed graph as the canonical file.** The step-3 files describe the deployed graph (after the converter's
   passes and the recipe's derive step), not the module structure of the PyTorch source: BatchNorm already folded,
   BiBERT's / Bi-ViT's GELU already replaced by the recipe's zero mask. The values are still the checkpoint's (the
   graph is rebuilt from it and must match the published hashes). The alternative, a module-by-module export with
   the passes in the importer, would need the derive step as an import option that changes values (not allowed by
   § 7). Confirm that the deployed graph is the right canonical form for these families.
4. **fp32 reference.** The fast fp32 reference (one onnxruntime session, `ORT_DISABLE_ALL`) and qonnx `execute_onnx`
   differ on float `Conv` / `MatMul` (execute_onnx's single-node sessions keep onnxruntime's own kernel
   optimizations; see Findings). Which one should the profile name as *the* fp32 reference? (B-class patterns are
   equal under both.)
5. **Ternary weights form.** The checker warns (`W-FLOAT-WEIGHTS`) on a plain `{−1, 0, +1}` constant although R4
   lists it as accepted; step 3 uses the other R4 form, `IntQuant(W, 1, 0, 2, signed, narrow)`. Make the checker
   accept the plain constant, or drop it from R4?
