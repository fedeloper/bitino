## 1. Recipes build through QONNX

Each route names the writer of every published file's canonical file:

* float files: the front end's writer, from the checkpoint (steps 1–4); the step-3 and step-4 writers rebuild the
  legacy adapter's parse in the recorded reference environment and check it against the published file before
  writing, as in their steps;
* int8_full files: `tools/export_int8_qonnx.py`, whose source is the published int8_full graph itself after its data
  and graph SHA-256 are checked against the recipe (step-5 decision: the quantizer's calibration images are not
  redistributed);
* derived files, below.

The importer then runs with `--model-id`, `--out-dir`, `--file-name` only. Identity is compared with
`artifacts/<id>/<file>` (read only) and, for the 233 files in the recipes' `expected`, with the recipe's hashes.

### Derived files

The derived files under `artifacts/` are `model_unfused.bitino` (128), `model_sign_zero_unfused.bitino` (56) and
the detector stages `model_features.bitino` / `model_network.bitino` (3 + 3). `tools/derive_variant.py` produces
none of them: its only pass (`drop_gelu_before_sign`) makes the published BiBERT / Bi-ViT `model.bitino` itself, which
step 3's canonical files already contain. The detector stages are a derivation of the published file
(`tools/ftl_deepfake_submodels.split`), so they are derived from the QONNX-built `model.bitino` (6 files).

The `*_unfused` files are **not** derivations of the published files: they are the legacy converters' graphs before
`passes.optimize(fold=True)`, and folding an affine into a convolution rounds products in float32, so the fused
`.bitino` does not determine them (checked: the fold passes on the published unfused file give the published fused
file for 127 of the 184, so the relation is one-way). They are built from the QONNX route instead, two ways:

| derivation | files | networks |
|---|---:|---|
| the parent's canonical file imported **without the fold passes** (`--no-fold`): the importer's graph before `passes.optimize` | 91 | IR-Net family (except ShuaiZ), AB-BNN ReActNet-18/34, ReActNet-A, RBONN / SNN / IDa-Det, SA-BNN, bitorch, BiMatting, BBCU super-resolution ×4, daBNN, NNCF, FDA-BNN, tensorpack, Larq DoReFaNet |
| a **canonical file of its own**: the converter's graph before its fold passes, rebuilt from the checkpoint with the legacy adapter in the converter's environment, required equal (data + graph) to the published file, written group-mapped (`tools/export_unfused_qonnx.py`; step 3: `tools/export_groups_qonnx.py`) | 65 + 28 | step 3 (Bi-ViT, GSB, BHViT, the 18 detectors: their canonical files hold the post-pass graph); BBCU denoise / deblocking and BNAS (ReLUs the adapter fuses itself); BSRC, AdaBin, BNext, ShuaiZ Bi-Real-20 (data in the adapter's creation order, not first use); Keras / Larq (the adapter fuses `activation=relu` into the binary conv); Brevitas, FINN, BNN-PYNQ (the literal BatchNorm + sign mirror instead of integer thresholds); OpenVINO (the parse before `merge_affine_chains`) |

The split was found by building every derived file with `--no-fold` first: 91 reproduce, 93 do not, for the reasons
in the table (each diagnosed against the published graph). A derived file's own canonical file is an ordinary
profile file (check-qonnx: no error; the BNAS float convs on binarized tensors are declared `bitino.float_layer`), so
each of the 486 files has a canonical QONNX file that determines it alone, or is the `--no-fold` import of one.

## 2. Every canonical file determines its `.bitino` alone

Steps 3–5 already recorded their mapping (`bitino.import {"mapping": "groups"}`) and step 4 its pattern options. Steps
1, 1b and 2 recorded their import arguments only in `export.json`; their writers now put them into the file:

| writer | `bitino.import` |
|---|---|
| `export_torch_qonnx.py` (CNN hooks) | `{"mapping": "patterns", "naming": "exporter", "constant_order": "first-use", "affine": "keep", "cleanup": "none", "bit_outputs": "set", "flatten_dense": "transpose"}` (VGG-Small: `"flatten_dense": "permute"`) |
| `export_torch_qonnx.py` (BBCU, BSRC image hooks) | as above with `"constant_order": "walk"` (their arguments named no order: the importer default) |
| `export_keras_qonnx.py` | `{"mapping": "patterns", "naming": "exporter", "constant_order": "first-use", "affine": "keep", "cleanup": "none", "bit_outputs": "none", "flatten_dense": "transpose"}` |

No value or name changes: the key is model metadata (outside the `.bitino`), and the sweep rebuilt every file of these
writers byte for byte with no import argument. The importer rule (§ 6 of the profile): with `bitino.import` the file is
the authority, an explicit argument must equal the file's value or, for an option the file does not list, the
importer default (so a step-4 file that lists no `flatten_dense` cannot be imported with `--flatten-dense permute`); a
group-mapped file accepts none; `--input-domain` must equal `bitino.input_domain` (every pattern-mapped file declares
`float32`). Tests: `test_pattern_file_determines_its_import`, `test_group_file_takes_no_import_argument`,
`test_writers_record_the_import_layout`.

## 3. Profile fixes

**Ternary constant (R4).** The checker warned `W-FLOAT-WEIGHTS` on a plain `{−1, 0, +1}` weight constant, which R4
allows; it is now info `I-TERNARY`; any other value still warns (`test_plain_ternary_weight_constant_accepted`).

**L8ENC.** The int8 log2 encoder is now

```
a = Abs(w)
c6 = Where(GreaterOrEqual(a, Gather(beta[127], 63)), 64, 0)                               (INT64)
c_j = Add(c_{j+1}, Where(GreaterOrEqual(a, Gather(beta, Add(c_{j+1}, 2^j - 1))), 2^j, 0))  j = 5..0
y = Cast(Mul(Cast(Sign(w), INT64), c0), INT8)
```

38 nodes, every intermediate of the shape of `w` (the step-5 form compared `|w|` with all 127 boundaries at once, a
`[…, 127]` tensor, ~0.5 GB per sample at a 112 × 112 × 64 stem). Why it is exact: the code is the number of boundaries
`β_k ≤ |w|` (step 5); β is strictly increasing, so with `N` that count (≤ 127, 7 bits) and `c` = `N` with its bits
below j+1 cleared, `β[c + 2^j − 1] ≤ |w| ⇔ N ≥ c + 2^j`, i.e. step j sets bit j of `N` exactly; the index stays ≤ 126.
**Proved exhaustively** (`tools/qonnx_l8enc_proof.py`, 572 s): on all 4,278,190,082 non-NaN fp32 bit patterns
(2³² − 2²⁴ + 2: both signs, ±0, subnormals, ±inf; NaN is outside the profile's A4) the writer's nodes in onnxruntime
(`ORT_DISABLE_ALL`), the numpy mirror and the step-5 count form all equal `int8_ops.l8_encode`: 0 mismatches. **Re-verified** with the step-5 acceptance (`tools/qonnx_step5_acceptance.py`,
the development log (not published)) on the 22 files with l8 outputs (the 20 `model_int8_full_log2.bitino` and
the `model_int8_full.bitino` of AB-BNN ReActNet-34 and ImageNet ReActNet-A): check-qonnx clean, data + graph
identical, every group re-emission-checked, and onnxruntime = C++ `int8_full` on all 2,816 check-set samples
(= `int8_full_reference` on 704, = numpy on 88, re-imported file = published in C++): 22 / 22 bit-exact. The files got
larger in nodes (e.g. 492 → 1,072) but onnxruntime ran the 128 samples 1.3–3.2× faster.

**fp32 reference.** Profile § 8 now names one onnxruntime session with `ORT_DISABLE_ALL` (the QONNX quantizers
replaced by their standard-op definitions, `bitino.qonnx_groups.ort_session`) as the fp32 reference, and qonnx
`execute_onnx` as the cross-check (equal on B-class patterns, float32 rounding apart on F-class nodes: § 2 A2). The
pattern importer's `verify` follows (checked on AB-BNN CIFAR-10 ReActNet-18: acceptance passes, `execute_onnx` within
1.1e-5 of the session on the first 4 samples, the A2 difference of a float `Conv`).

## Not done, and design decisions

Nothing of the five tasks is open; every file is identical. Points that are scope or form:

1. **`bitino fetch` still runs the legacy converters.** The recipes in `registry/recipes.json` (and the `bitino
   fetch` code) are part of the public export; switching their `steps` to the QONNX writers would change public
   files and needs the writers' environments (`.cache/venv-qonnx2`, `venv-larq`, the conda envs of step 3) in the
   recipe environments. The QONNX route is recorded separately in `registry/qonnx_routes.json` and run by
   `tools/build_from_qonnx.py`. Switch `fetch` (and publish the writers), or keep fetch as the public legacy path?
   **Switched (2026-11-23, development tree only, nothing exported):** the recipes' `steps` are the QONNX route and
   the converters are `crosscheck.steps` (`fetch --legacy`); see
   [qonnx-standard.md § bitino fetch](qonnx-standard.md#bitino-fetch-the-users-build-path).
2. **The `*_unfused` files are converter by-products, not derivations** (§ 1). 91 are the `--no-fold` import of the
   parent's canonical file; 93 have canonical files of their own written from the legacy adapter's pre-pass graph
   (the step-3 precedent). Keep both forms, or redefine the unfused files as the importer's pre-pass graph (`--no-fold`
   of every parent: 93 files would change their bytes), or stop keeping them?
3. **The legacy adapters stay in the build path's writers.** The step-3 / step-4 / unfused writers read the source
   with the legacy adapters and the converters' load functions (the canonical files are written from that parse);
   only the converters' IR emission and validation are retired. Deleting `tools/convert_*.py` would need their load
   functions moved first.
4. **int8_full canonical files are written from the published int8_full graphs** (step-5 decision, unchanged): their
   source is the published file (hash-checked), not a quantizer run, because the calibration images are not
   redistributed.
5. **Profile additions of this step** (each changes no value, enforced by the importer): `bitino.import` in effect
   required, `I-TERNARY`, the L8ENC bisection, the group-mapping constructs of § 7 (Activation sign, IR Pad, explicit
   `Pad(0)` before a float conv on a binarized tensor, `BDense activation` as an added default, the informational
   `pad_value` of an unpadded `BConv2D`). Confirm.

Housekeeping: the run wrote only under `.cache/qonnx_step6/` (logs, scratch; deleted after each row), never above
~2 GB transient; free disk was 35.9 GB at the start (already below the 36 GB mark, from other jobs) and 37.0 GB at the
end. Memory caps: at most 10 GB in total for this step's jobs; a 3 GB scope was too small for TensorFlow and the BNext-M
/ -L / BNAS-H exports (OOM, rerun larger).
