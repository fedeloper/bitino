Plan: [qonnx-frontend.md § Plan](qonnx-frontend.md#plan), step 5. Date: 2026-11-21, host only (x86-64), nothing under
`artifacts/` was written, registry hashes untouched. Machine-readable results: the development log (not published)

**Identity bar (design decision 2026-11-20, docs/qonnx-profile.md Q11).** The re-imported `.bitino` has the published
file's data SHA-256 and graph SHA-256 (= `registry/recipes.json` → `expected[<file>]`): every constant byte in the same
order, the same graph JSON, every layer, node, tensor and constant name byte for byte; the manifest is not compared.
**Numerical bar (int8_full):** the integer outputs are a bit-exact contract, so the canonical file evaluated by
onnxruntime in its declared element types must give the C++ runtime's `int8_full` outputs **bit for bit** on the check
set (no tolerance).

**Result: 101 published int8_full files of 81 networks: every file rebuilds from its canonical QONNX file with the
published data and graph SHA-256** (= the recipe's expected hashes), every canonical file passes `check-qonnx` with
no error and no warning, every one of the 15,664 groups passes the importer's re-emission check, and **all 101 are
bit-exact**: onnxruntime on the canonical file reproduces the C++ runtime's `int8_full` outputs byte for byte on every
sample of the check sets (128 per file, 12,928 samples in all), and equals the C++ `int8_full_reference` stage (first
32 samples of every file), the numpy oracle (first 4) and qonnx `execute_onnx` (first sample of the 26 CIFAR-size
files). Nothing is "not done", no int8 operator needed anything outside standard ONNX + QONNX, and no design decision
blocks a file (the decisions below are about form). The two onnxruntime defects named in the task are worked around
with standard operators (INT64 `Clip` near 2^31: `Where` saturation; `ConvInteger` padding: explicit `Pad` of the
pad code), § [onnxruntime behaviours](#onnxruntime-behaviours-worked-around-standard-ops-only).

### The source of the canonical files: the published int8_full graph

Steps 1–3 rebuild the float graph from the checkpoint and require the rebuilt graph to have the published hashes
before writing the canonical file. An int8_full file is the output of the quantizer (`tools/quantize_int8_full.py`)
on the float file and **calibration images that are not redistributed** (the training splits; `registry/recipes.json`
marks every int8 step `reconstructed`, not a runnable recipe, and records the calibration tensor's SHA-256 and the
sample ids in the manifest). The writer therefore reads the published int8_full file itself (read only), after
checking its data and graph SHA-256 against the recipe: the canonical file is the exact description of the deployed
integer graph, with the values the quantizer chose. The source checkpoint, the calibration set (`bitino.calibration`:
set, split, n, tensor SHA-256) and the quantizer options are recorded in the metadata. Re-running the quantizer is not
part of this step (decision 1 below).

### One group per int8 IR node, with a re-emission check

As in step 3, every IR node of the published graph becomes one group of standard nodes (`bitino.name`,
`bitino.order`, `bitino.consts`, `bitino.ir`, `bitino.attrs`), in the pattern of docs/qonnx-profile.md § 5. 4-D image
tensors are NCHW (the graph input, every spatial `I8*` operator: `I8Conv2D`, the binary convolutions and fused blocks,
the pools, `I8GatedAdd`, `I8GapAffine`, and the per-tensor element-wise operators between them); all other tensors keep
the IR's shape (tokens, attention maps, BHViT's windows), with explicit layout `Transpose`s. Element types follow the
IR: INT8 codes, ±1 FLOAT bit tensors, FLOAT values, INT32 token ids; every integer epilogue is INT64.

The importer reads each group in two steps. The extractor `r_<op>` (one function per operator) walks the group from
its output back through the writer's primitives and recovers the IR node: its runtime inputs, its constants (named by
`bitino.consts`, unpacked from the derived ONNX constants: `M`, `shift` from the `REQUANT` chain, OHWI kernels from
OIHW ±1 weights, `qpm` from the bit-table gather, ...) and its attributes (from the constants and the ONNX attributes).
Then the writer **re-emits** the group from that IR node, and the importer requires the re-emitted nodes to equal the
file's group node for node: operator, domain, attributes, and every input (the same external tensor, the same
internal producer, or a constant with the same element type, shape, bytes and carrier status). A group that computes
the same values in another form, or carries a constant that the extracted node would not produce (a rounding term
2^(n−1) that does not match its shift, a table that is not `l8_decode`), is rejected. All 15,664 groups of the 101
files pass the check (`reemission_checked_groups` in the summary).

| the IR's form of a derived axis (per-channel I8Lut `axis: 1`) | `bitino.attrs` rule (d) | 4 (BHViT) |
| absent attributes at the operator's default (`qmin` / `qmax` of I8Mul, I8LayerNorm, I8BMatMul, `dilations` / `groups` of the BHViT patch I8Conv2D, ...) | `bitino.attrs` null (step 3 rule (a), with the int8_ops defaults) | many |

None of them changes a value; rule (c) is the only place where metadata supplies an attribute value, restricted to
attributes that the operator does not read (int8_ops / the C++ kernels) in that node's configuration.

### onnxruntime behaviours worked around (standard ops only)

| behaviour (onnxruntime 1.31.1) | work-around in the canonical files |
|---|---|
| `Clip` / `Min` / `Max` on INT64 compare inexactly near 2^31 (profile § 2) | every INT64 saturation (`sat32` of the requantization, the `[qmin, qmax]` clamps, the pre-stage clamps of `I8BConv2DResI`, whose bounds are `±2^31` exactly) is `Where(Greater(a, hi), hi, a)` → `Where(Less(·, lo), lo, ·)`; INT32 is never clamped with `Clip` either |
| `ConvInteger` padding reads the zero point (a padded tap contributes 0), not defined by the ONNX text | `ConvInteger` always has `pads = 0`; the padding is an explicit `Pad` with the IR's `pad_q` (I8Conv2D) or `x_zero` (I8AvgPool2D, where the padded tap must contribute `z − z = 0`) |
| `BitShift` exists for unsigned types only; integer `Div` rounding is not fixed by the ONNX text | arithmetic right shifts are the UINT64 offset construction `ASR` (profile § 5, Q6); the average-pool division is `RDIV` in DOUBLE |
| no `ReduceSum` / `MatMul` kernel for INT8 | INT8 codes are cast to INT32 / INT64 before a reduction; integer GEMMs are `ConvInteger` / `MatMulInteger` (both checked bit-exact with INT8 activations and zero points, grouped / dilated / strided / batched) |
| unused initializers are dropped with a warning | harmless: `bitino.unused_constants` never feed a node |

## Findings

* **No custom operator was needed, and no int8 operator was stopped for an inexpressible construct.** Every one of the
  29 operator types of the 101 files is written with standard ONNX operators (plus the QONNX `BipolarQuant` / ternary
  `IntQuant` of the binary layers) and is bit-exact in onnxruntime in the file's element types. The requantization
  (SQRDMULH + rounding shift) is INT64 arithmetic with the UINT64 `BitShift` offset construction, every saturation a
  `Where`, the log2 code a 256-entry `Gather` (decode) and the 127-compare count (encode), the LayerNorm / Softmax row
  factors DOUBLE operations in the kernels' order, the average-pool division a DOUBLE floor quotient.
* **The int8 binarization is written on the dequantized value, not as integer thresholds.** The profile draft had
  `BIN8(q; T)` with the kernels' integer thresholds `T_ge` / `T_gt`; the IR stores `(x_scale, x_zero, threshold)` and
  derives `T` from them (many-to-one), so a `T` form cannot be imported to the published bytes. `Bin(DEQ(q) − t)` is
  the definition the kernels implement (`deq` non-decreasing ⇒ `deq(q) ≥ t ⇔ q ≥ T_ge(t)`), exact in fp32, and keeps
  the attributes (profile § 5 `BIN`).
* **The guarded `I8Gather`.** The IR's `fill_q` (the code of an out-of-range id) is part of the node; the plain
  `Gather` on a declared domain (step 3, Q7) cannot carry it, so the int8 gather is the guarded form
  `Where(in_range, Gather(T, Where(in_range, ids, 0)), fill_q)`, exact for every id.
* **Identity needed three new naming facts** (above): IR output names (`bitino.ir.outputs`, every file), informational
  attributes (`bitino.attrs` rule (c)) and unused constants (`bitino.unused_constants`, 3 files). The published files'
  `y_exp` attributes, unpadded `pad_value`s, `count_include_pad`s of windows that never reach the padding, and the
  `zeros` / `shifts` of copied I8Concat inputs are read by no kernel, so no pattern can carry them.
* **onnxruntime facts** (profile § 2): no `ReduceSum` / `MatMul` for INT8; INT8 `ConvInteger` / `MatMulInteger` with
  INT8 zero points are exact (grouped, dilated, strided, batched); float `Conv` / `MatMul` of ±1 operands are exact sums
  below 2^24; the INT64 `Clip` and the `ConvInteger` padding behaviours of step 0 are avoided by construction. A
  session's memory arena and memory-pattern planner keep several GB for the 224 × 224 networks' INT64 epilogues; the
  acceptance disables both (values unchanged).
* **The C++ runtime, the numpy oracle and onnxruntime agree everywhere they were compared** (table above): the
  int8_full contract (int8_ops = C++ reference = optimized kernels) is now also expressed, and checked, as a standard
  ONNX graph.
* **Cost.** The canonical int8 files are larger than their `.bitino` (±1 weights unpacked to INT8, the epilogues'
  derived constants) and have 258,334 ONNX nodes for the 15,664 IR nodes (16.5 per group on average; the `REQUANT` chain alone is 18); onnxruntime runs them
  in 0.03–2.6 s per sample on one thread (BNext-L the slowest). The L8ENC `[…, 127]` comparison is the largest
  intermediate (Q5).

## Not done

Nothing. All 101 published int8_full files are identical and bit-exact. Limits of the scope, none of which is used by a
published file: the writer has no pattern for the `I8BConv2DResI` PReLU pre stage (input 15), the `I8GatedAdd` gate
table (input 7), the `I8Conv2D` / `I8Dense` bit output with a float output, `I8Lut` per channel in an NCHW group, the
`I8GlobalAvgPool` / `I8ReduceMean` division form (without `mult`), and the int8_full operators that no published file
contains (`I8BConv2DResIX`, `I8DctYuv420`, `I8BConvBP`, `I8ArgMax`, `I8ChannelShift`, `I8BinarizeDyn`, `I8SimAM`);
each is refused with a precise error, not approximated. The re-imported files' manifests are regenerated (not
compared). The canonical files are 0.4–339 MB (2.8 GB in all) and were deleted after their rows (their SHA-256 are in
the summary); regenerate them with `tools/export_int8_qonnx.py`.

### Running it

This run: four shards of `tools/qonnx_step5_acceptance.py` under `scripts/capped.sh` at 1.5 GB each, then the files
whose export / import needs more memory (the canonical file is held several times: build, check, save, load) one by
one at 3–4.5 GB (BiBERT ×4, BNAS-H, BNext-T / S at 3.5 GB, BNext-M at 3 GB, BNext-L and tensorpack AlexNet at
4.5 GB); never more than 8 GB of caps at once. Work files in the session tmpfs. Wall time: 30–60 s per CIFAR file,
2–5 min per ImageNet ResNet, about 10 min per BiBERT file, 45 min for BNext-L (the C++ reference kernels
dominate; onnxruntime takes from 4 s (CIFAR) to 5.5 min (BNext-L) per file for 128 samples). Per-file reports: `.cache/qonnx_step5/<id>/<file>.json`;
the shards' rows are merged into the development log (not published).

2. **Informational attributes (`bitino.attrs` rule (c)).** Attributes that no kernel reads in the node's configuration
